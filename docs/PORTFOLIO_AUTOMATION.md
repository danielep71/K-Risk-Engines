# Daily portfolio refresh

The `Daily portfolio refresh` Actions workflow runs nominally at **07:00 Europe/Rome**,
including daylight-saving time, and can be run manually. GitHub schedules may be
delayed. The schedule uses GitHub's native `Europe/Rome` timezone support.

It reads the four public repositories in `.github/portfolio.json`: their default
branch README, selected evidence documents, published stable releases, and all
milestones. It chooses the last closed milestone by `closed_at`, not version
number, issue count or last modification date. A reopened milestone is excluded.
Closure dates are displayed as the GitHub API's UTC calendar date.

The workflow updates only the hub's marked README table and website status
blocks, plus `docs/PORTFOLIO_STATUS.md` and `docs/portfolio-state.json`. Project
purpose copy remains maintainer-owned. Source status passages are quoted in full
(formatting removed and HTML escaped), not generated by an LLM. The website keeps
the longer passages in an expandable status-and-limitations section. Existing
stage badges are replaced by the neutral “Project snapshot” label, so an old
curated stage cannot conflict with new evidence. The snapshot is not a certification.

## Review and publication

- Changes are proposed on `automation/portfolio-refresh` in one reusable PR,
  assigned to `danielep71` with `documentation` and `P3` labels. Nothing automatically merges or publishes to main.
- The proposal includes pinned README/evidence links, hashes, release data and
  milestone records. Changes to evidence files trigger review even if the status
  wording itself is unchanged. Evidence is read, never executed.
- README status selectors are explicit. Missing, ambiguous or unexpectedly long
  status passages, missing evidence files, rate limits and API/network failures
  abort collection before writing any proposal files. Inspect the failed run;
  do not reinterpret a failed lookup as “no release” or “no milestone”.
- A source commit with no changes to tracked content does not trigger a PR.
  No daily timestamp-only commits are made. Issue-count changes within a
  milestone are recorded as tracking progress, not model readiness.
- Review the source wording and any contradictions between release and current
  development status before merging. A closed milestone or passing CI does not
  prove Excel execution, numerical validation or regulatory readiness.
- Treat the proposal branch as generated content. Merge conflicts stop the run
  for review; it never force-pushes. Closing an unmerged PR without changing the
  sources can result in a new proposal on the next run. Disable the workflow to
  pause proposals.

## Permissions and checks

Uses the repository's built-in `GITHUB_TOKEN`, with `contents: write` and
`pull-requests: write` only in the refresh job. No PAT, external AI service,
engine-repository write access or analytics secret is required. Public engine
metadata is read using GitHub's API.

GitHub must allow **Actions to create pull requests** in repository Settings →
Actions → General → Workflow permissions. Keep the default token permissions
read-only; this job requests its own limited write permissions. If the repository
setting blocks PR creation, the run fails and the prepared branch remains
available. Enabling that setting is a separate maintainer action.

PR workflows created by `GITHUB_TOKEN` can require a maintainer to approve their
execution. The refresh job therefore runs HTML/internal-asset checks, external-link checks and the
portfolio regression tests before pushing without relying on downstream PR CI. External-link warnings remain visible
in logs and do not establish successful reachability. A normal maintainer merge
triggers main's website checks and Pages deployment.

Local dry run (writes only local generated files):

```sh
python3 .github/scripts/portfolio-refresh.py --body-file /tmp/portfolio-pr.md
python3 -m unittest discover -s .github/scripts -p 'test_portfolio_refresh.py'
python3 .github/scripts/check-website.py
```

Set `GH_TOKEN` only through a configured environment if needed for GitHub API
rate limits. Never commit credentials. Updating `.github/portfolio.json` or the
selectors requires reviewing the affected source documents and tests.

Use `--render-only` to reproduce the generated pages from the committed snapshot
without network access; this does not check for newer project evidence.
