# 🔄 Daily portfolio refresh

[![portfolio refresh](https://img.shields.io/github/actions/workflow/status/danielep71/K-Risk-Engines/portfolio-refresh.yml?branch=main&style=flat-square&label=portfolio%20refresh)](https://github.com/danielep71/K-Risk-Engines/actions/workflows/portfolio-refresh.yml)
[![Schedule](https://img.shields.io/badge/Schedule-07:00_Europe%2FRome-1f3a5f?style=flat-square)](https://github.com/danielep71/K-Risk-Engines/actions/workflows/portfolio-refresh.yml)
[![Proposals](https://img.shields.io/badge/Proposals-GitHub_App_token-483698?style=flat-square)](#permissions-and-checks)

The `Daily portfolio refresh` Actions workflow runs nominally at **07:00 Europe/Rome**,
including daylight-saving time, and can be run manually. GitHub schedules may be
delayed. The schedule uses GitHub's native `Europe/Rome` timezone support.

It reads the public repositories configured in `.github/portfolio.json`: their default
branch README, selected evidence documents, published stable releases, and all
milestones. It chooses the last closed milestone by `closed_at`, not version
number, issue count or last modification date. A reopened milestone is excluded.
Closure dates are displayed as the GitHub API's UTC calendar date.

A milestone that the source repository deletes stays in `docs/portfolio-state.json`
with its last recorded state and counts, no URL and a `removed_on` date (UTC) set
by the refresh that first misses it. The status report lists it as a historical
snapshot without a link, and it is never chosen as the last closed milestone. Do
not edit `docs/PORTFOLIO_STATUS.md` for this: change the stored state or the
renderer, so that `--render-only` reproduces the report.

Repository paths in the generated files come from GitHub's API, so after an
engine repository is renamed the generated links point to its new name at the
next refresh. Displayed project names come from the `name` field in
`.github/portfolio.json` and do not follow a rename. After a rename, update the
`repo` field, and the `name` field if the displayed name should change, in
`.github/portfolio.json`; the issue chooser in
`.github/ISSUE_TEMPLATE/config.yml`; and the README and the website's
hand-written card and heading links.

The workflow updates only the hub's marked README table and website status
blocks, plus `docs/PORTFOLIO_STATUS.md` and `docs/portfolio-state.json`. Project
purpose copy remains maintainer-owned. Source status passages are quoted in full
(formatting removed and HTML escaped), not generated by an LLM. The website keeps
the longer passages in an expandable status-and-limitations section and shows
them without links: each project is linked only from its card, while the README
table and `docs/PORTFOLIO_STATUS.md` keep the source and milestone links. Existing
stage badges are replaced by the neutral “Project snapshot” label, so an old
curated stage cannot conflict with new evidence. The snapshot is not a
certification. `docs/PORTFOLIO_STATUS.md` is generated: change its renderer in
`.github/scripts/portfolio-refresh.py` for presentation fixes, and use a normal
refresh for new source evidence. Do not hand-edit
quoted statuses or milestone counts; the next run would overwrite them.

## 👀 Review and publication

- Changes are proposed on `automation/portfolio-refresh` in one reusable PR,
  assigned to `danielep71` with `documentation` and `P3` labels and no milestone,
  because a proposal is not release work. Nothing automatically merges or publishes to main.
  The maintainer merges an accepted proposal with a merge commit, the only
  method `main` accepts (see [GOVERNANCE.md](../GOVERNANCE.md)). GitHub then
  deletes the proposal branch, and the next refresh recreates it from `main`.
- The proposal includes pinned README/evidence links, hashes, release data and
  milestone records. Changes to evidence files trigger review even if the status
  wording itself is unchanged. Evidence is read, never executed.
- README status selectors are explicit. Missing, ambiguous or unexpectedly long
  status passages, missing evidence files, rate limits and API/network failures
  abort collection before writing any proposal files. Inspect the failed run;
  do not reinterpret a failed lookup as “no release” or “no milestone”.
- A source commit with no changes to tracked content does not trigger a PR.
  No daily timestamp-only commits are made. Issue-count changes within a
  milestone are recorded as tracking progress, not model readiness.
- Review the source wording and any contradictions between release and current
  development status before merging. A closed milestone or passing CI does not
  prove Excel execution, numerical validation or regulatory readiness.
- Treat the proposal branch as generated content. Merge conflicts stop the run
  for review; it never force-pushes. Closing an unmerged PR without changing the
  sources can result in a new proposal on the next run. Disable the workflow to
  pause proposals.

## 🔐 Permissions and checks

The job runs only from `main`, in the `portfolio-refresh` environment. Token
use is scoped to different steps:

- The refresh, the website checks, the external-link checks and the script
  tests use the job's read-only `GITHUB_TOKEN` (`contents: read`) to read
  public engine metadata. Their steps are not passed the App token.
- Only when there is a change to propose does the job mint a short-lived token
  for the **K-Risk Portfolio Refresh** GitHub App, limited to this repository
  with `contents: write` and `pull-requests: write`, and use it solely to push
  `automation/portfolio-refresh` and open or update the pull request.

These steps share one runner and workspace; step-scoped token variables are
not a security isolation boundary. Changes to the workflow or scripts must be
reviewed before running them on `main`. The environment's branch restriction
also does not restrict access to this particular workflow identity.

Pull requests opened with `GITHUB_TOKEN` wait for a maintainer to approve their
workflow runs. Pull requests opened with the App token do not, so **Website
checks** run on every proposal without an approval prompt. The code-review bot
does not review pull requests opened by bots, so the maintainer's review before
merging is the only review of a proposal. No PAT, external AI service,
engine-repository write access or analytics secret is required.

### 🛠️ One-time App setup (maintainer)

1. **Settings → Developer settings → GitHub Apps → New GitHub App**: name it
   (for example "K-Risk Portfolio Refresh"), set the homepage to the website,
   untick **Webhook → Active**, grant only the repository permissions
   **Contents: Read and write** and **Pull requests: Read and write**, and make
   it installable **Only on this account**.
2. In the App, open **Credentials → Key pairs** and generate a private key. The
   browser downloads a `.pem` file once.
3. **Install App** on this account for **Only select repositories →
   K-Risk-Engines**.
4. In this repository, **Settings → Environments → New environment →
   `portfolio-refresh`**: restrict deployment branches to `main`, add the
   variable `PORTFOLIO_APP_CLIENT_ID` (the App's Client ID, not secret) and the
   secret `PORTFOLIO_APP_PRIVATE_KEY` (the whole `.pem`, including the BEGIN and
   END lines). Delete the downloaded file afterwards.
5. Run **Actions → Daily portfolio refresh → Run workflow** on `main`. When
   there is something to propose, the run summary links the pull request and
   **Website checks** start on it without an approval prompt. A missing
   variable, key or installation fails the **Create GitHub App token** step.

Rotate the key by generating a new one, updating the secret, and deleting the
old key in **Key pairs**. To pause proposals, disable the workflow.

If a proposal pull request stays open while workflow files change on `main`,
the next run's merge of `main` into the proposal branch touches workflow files,
which the App is deliberately not allowed to push. Merge or close the pending
proposal (deleting its branch) and run the workflow again.

The refresh job runs the HTML, Markdown-link, external-link and script tests
before pushing, and **Website checks** run again on the pull request. External-link
warnings remain visible in logs and do not establish successful reachability. A
normal maintainer merge triggers main's website checks and Pages deployment.

### 🧪 Local dry run

This writes only local generated files:

```sh
python3 .github/scripts/portfolio-refresh.py --body-file /tmp/portfolio-pr.md
python3 -m unittest discover -s .github/scripts -p 'test_*.py'
python3 .github/scripts/check-website.py
```

Set `GH_TOKEN` only through a configured environment if needed for GitHub API
rate limits. Never commit credentials. Updating `.github/portfolio.json` or the
selectors requires reviewing the affected source documents and tests.

Use `--render-only` to reproduce the generated pages from the committed snapshot
without network access; this does not check for newer project evidence.
